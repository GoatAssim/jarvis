## (a) Text for AGENTS.md / REPO_MAP.md / the guide

### REPO_MAP.md (two rows)

- `jarvis-cli/jarvis/modhosts/apply.py` - the ONE engine that replaces a mod file of the owner's: `apply_update(folder, old_sha1,
  plan_entry, *, dry_run, deadline_seconds)`. Finds the old file by SHA-1, re-reads the new file's link and hashes from the same
  adapter that found it, downloads through `net.fetch` into `~/.jarvis/modhosts/replaced/_staging/`, verifies size and hash on disk,
  moves the OLD file to `~/.jarvis/modhosts/replaced/<YYYYmmdd-HHMMSS>/`, moves the new one in without replacing anything, verifies
  again, writes `replaced.json`, prunes old backups. Also the record helpers (`read_record`, `write_record`, `batch_ids`) and
  `_remove_batch`, the only function in the Minecraft group that deletes anything the owner could want back.
- `jarvis-cli/jarvis/actions/minecraft_undo.py` - `list_mc_replaced` (read) and `undo_mc_update` (confirm-gated, owner only).

### AGENTS.md (Minecraft section; replaces the sentence that says nothing in the group replaces a file)

> **A mod file is replaced only by `modhosts/apply.py`** (called by `apply_mc_update`, owner confirmation or the owner's own
> standing auto-update tick), only inside a folder on the owner's watched list, never deleting anything - the old file is MOVED to
> `~/.jarvis/modhosts/replaced/<id>/` - and always verified by hash before and after. One file per call. A file with no published
> hash is refused (stricter than `download_mc_file`: here a bad file would replace a good one).
>
> `apply.py` rules: a record (`replaced.json`) is written BEFORE the old file moves (no record, no swap); the new file is placed with
> `outdir`'s no-clobber move and never over an existing name; if the second move fails the old file is moved back; a lock (Windows,
> game running) is reported as "close Minecraft and try again" and changes nothing; a move across drives is copy, verify the copy,
> then remove the source. Backups are pruned only after a SUCCESSFUL apply: oldest batch first, never the newest, at most
> `MAX_BATCHES` (50) or `MAX_BACKUP_BYTES` (2 GB). `_remove_batch(id)` is the only deleting code; it refuses anything that is not a
> batch folder directly inside `~/.jarvis/modhosts/replaced/` (name, real path, never a link). Tests pin this by AST scan.
>
> `list_mc_replaced` / `undo_mc_update` are OWNER ONLY (add both to `tools.OWNER_ONLY_TOOLS`) and refuse a guest themselves before
> any file is read. `undo_mc_update` moves the new file aside to `replaced/undone/<id>/` and puts the old file back, only when the file
> in the folder still has the hash the record says, the backup copy still has its hash, and the old name is free. Never overwrites,
> never deletes.

### Guide (user-facing, Minecraft > Updates)

When you apply an update, Jarvis downloads the new file, checks its checksum, puts your old file in
`~/.jarvis/modhosts/replaced/<time>/` (never deleted) and puts the new one in your mods folder. Restart Minecraft afterwards. To go
back, ask "undo the last mod update" (or use Undo in the Updates tab): Jarvis swaps the old file back unless you changed the new one
since. Close Minecraft first on Windows: a jar the game has open cannot be moved. Jarvis keeps the last 50 backups (or 2 GB) and
removes the oldest one after a later update succeeds. A file with no published checksum is never replaced.
